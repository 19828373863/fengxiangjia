# Android 动效与相机采集（Issue #72）

本轮已实现原生界面动效、扫描准备状态修正和扫描房间导入坐标修正。当前相机入口仍是 **ARCore 连续画面跟踪 + 用户标记墙角/门窗**；普通多照片、导入视频、SfM/MVS 点云或三维网格重建均未实现。相机入口存在，不代表已经完成真实房间测量验收。

记录日期为 2026-10-13，工作分支为 `feat/72-native-motion-and-camera`。源码版本为 Android 0.2.1 / versionCode 3。本文对应原始工作仓库的 Motion.kt、MainActivity.kt、HomeScreen.kt、SuggestScreen.kt、RoomCanvas.kt、TrialScreen.kt、scan/ScanSupport.kt、scan/ScanActivity.kt 和 AppModel.kt；只读镜像保持原样。共享数据/schema、本机 session 与正式 Play 权益契约没有因这轮动效和扫描修复改变。颜色、字号、圆角和间距沿用 DESIGN.md。

## 原生动效：实际使用与停止条件

| 词汇或交互 | 当前源码实现 |
|---|---|
| Quick | 120 ms：页面退出淡出、展开区淡入/淡出、风扇选择反馈与试摆摘要 Crossfade。 |
| Standard | 220 ms：页面进入淡入/水平位移、展开区高度展开、建议页箭头展开。 |
| Exit | 160 ms：页面退出位移、展开区高度收起及建议页箭头收起。 |
| Settle | 280 ms，仅在 FxjMotion 定义，当前没有调用；没有据此实现回弹或弹簧。 |
| 显式缓动 | `CubicBezierEasing(0.2, 0, 0, 1)`。位移、展开、箭头、选择与摘要在调用处使用；没有显式 easing 的 fade tween 保留 Compose 默认值。 |
| 切页 | 根据目的地索引方向以 24 dp 进入/退出；进入淡入及位移 220 ms，退出淡出 120 ms、位移 160 ms。 |
| 折叠区 | MotionReveal 从顶部展开 220 ms / 收起 160 ms，配对 120 ms 淡入/淡出。用于我家的环境/隐私区，以及建议页进度、摆位详情、天气、朝向、购买与隐私区。 |
| 建议箭头 | 0°/180° 之间展开 220 ms / 收起 160 ms，与高度过渡配对；我家入口仍显示文字「展开/收起」。 |
| 风扇选择 | 120 ms 将 fan/方向线的 primary 颜色插值至 onPrimaryContainer，27 dp 光圈透明度随选择进度升至 0.14；关闭动效或非交互预览直接到目标状态。 |
| 试摆摘要 | 高度固定为 `72 dp × max(fontScale, 1)`，120 ms Crossfade；选择物品不改变加权画布的高度与视口。 |

过渡保留旧画面仅用于视觉连续性。离场页面通过 inactiveMotionContent 消费初始触控事件并清除无障碍语义，且关闭该页自定义动效；离场摘要的旧按钮被禁用并清除语义。用户编辑、保存和计算不等待过渡结束。原生底部面板、涟漪与进度指示仍由 Material 3 管理；没有引入 GSAP 或网页动画运行时。

rememberSystemMotionEnabled 实时监听 Android `ANIMATOR_DURATION_SCALE`，值为 0 时关闭自定义动效；LifecycleObserver 以至少 STARTED 作为前台门槛。关闭后切页/展开采用无过渡，风扇选择与摘要直接到目标状态。这里的动效前台门槛与扫描准备的 RESUMED 门槛分别处理，不混为一个判断。

### 有限风向提示

风向提示来自当前同一 FlowVisualization，最多选取 12 条已有有效流线；不另造流场、箭头或几何。相位用 LinearEasing 在 2400 ms 内从 0 到 1，提示点沿既有线段移动，完成后消失，相同当前 hash 不反复启动。它帮助看懂方向，**不是空气的真实速度、传播时间或位移测量**。

仅交互试摆图、当前结果有效、允许动效、没有拖动时播放。打开属性/物品/结果面板、保存对话框或开始导出会关闭播放条件；结果过期、离场页面、后台、缩减动效也使其取消。房间、A/B 和建议的非交互预览保持静态。

完整房间/风线绘制在独立 graphicsLayer，有限提示放在单独 overlay Canvas；相位只在绘制时读取，避免每个提示 tick 重组编辑界面并重画全部流线。这是源码结构说明，不是已测得的帧率或所有设备性能结论。

## 相机入口：当前能力与修正

### 支持状态是五种状态

| 状态 | 代码判断与界面含义 |
|---|---|
| SUPPORTED | SDK 明确返回 SUPPORTED_INSTALLED；当前前台准备完成后才拉起扫描。 |
| NEEDS_INSTALL | SDK 返回支持但 AR 服务未安装/版本过旧；用户明确点击「安装服务并继续」。 |
| CHECKING | SDK 暂态查询；每 300 ms 再查一次，最多等待 8000 ms。查询未完成不是扫描失败。 |
| UNSUPPORTED | 仅 SDK 明确返回 UNSUPPORTED_DEVICE_NOT_CAPABLE 才显示不支持。 |
| UNKNOWN | 其他未确认状态、异常或 8000 ms 超时；说明无法确认并保留重新检查/手动创建入口，不把它改称硬件不支持。 |

MainActivity 的准备对话框可取消，取消会取消检查协程。onStop 取消正在 CHECKING 的准备；检查结果只在 Activity 至少 RESUMED 且请求仍有效时继续，避免离场后自动拉起相机。

ScanActivity 先 requestInstall 验证/安装 AR 服务，再申请 CAMERA；INSTALL_REQUESTED 时等待平台流程。相机权限成功回调继续同一次采集，而不是停在无会话的摄像头界面。拒绝权限、取消安装、兼容性或会话启动异常均有明确提示与手动入口；onPause 暂停 GL surface 和 Session，onDestroy 关闭 Session。

ARCore 支持依赖机型/系统认证和兼容服务，Depth 支持另外检查。官方 Google Play 与 Android（China）设备/服务分发说明分别列出；中国区服务可由指定厂商应用商店提供，不能把“没有 Play Store”推广为所有 Android 的不支持条件。[ARCore 设备与中国区说明](https://developers.google.com/ar/devices?hl=en) 创建 Session 前仍须完成运行时安装、配置和相机权限检查。[启用 ARCore](https://developers.google.com/ar/develop/java/enable-arcore)

### 当前采集是怎样得到房间初稿的

GLSurfaceView 连续读取 AR 帧，Session 启用水平/竖直平面识别、自动对焦、最新相机图像；设备明确支持时才启用 AUTOMATIC Depth。相机未 TRACKING 时提示慢移，识别到地面后，用户依次点按地面墙角；竖直平面在角点不足时作为 core 转换的后备。

门窗仍需手动标记。当前代码使用门宽 0.9 m、窗宽 1.2 m 的初始值，结果进入编辑器后必须核对实际尺寸；层高来自命中点的粗略估计。完成后由 CaptureSession/ScanImport 转成二维 Room，并返回警告供编辑器校准；这不是全自动识别完整住宅、精确量尺或三维网格重建。

ARCore 本身结合时序相机特征与运动传感器跟踪位置/方向，更新平面与特征，低纹理表面的检测可能不稳定。由此推论，运行中的连续跟踪不能由单张普通照片等价替代。[ARCore 基本概念](https://developers.google.com/ar/develop/fundamentals)

### 导入坐标修正

外部扫描使用自己的局部原点。AppModel.importRoom 先减去输入 polygon 的 minX/minY，再将新房间放到已有房间最大 Y 的上方 1 m；同一 offset 应用于 polygon、fan、家具中心及目标形状。门窗继续使用宿主墙上的局部 offset。修正后不能因为扫描的原点本来有偏移而把新房间叠到旧房间上。

导入仍经过有限值、几何、房间重叠和实体校验；拒绝无效结果时保留已有住宅。新增房间不改变共享 schema v2，也不把照片/视频塞入主 JSON。本轮不引入画面上传、相册导入或云重建服务。

## 多照片或视频：可研究的独立路线

| 路线 | 当前 APP 状态 | 输入、输出与条件 |
|---|---|---|
| 现有 ARCore 采集 | 已有源码，真实量测仍未通过 | 连续跟踪帧 + 手动墙角/门窗，生成可校准二维 Room；设备/服务和现场跟踪必须满足。 |
| 多照片 SfM → MVS | **未实现** | 同一场景从不同视点拍摄、有重叠的清晰照片；SfM 求稀疏结构和相机参数，MVS 再生成较密几何，不直接等于房间拓扑。 |
| 视频抽帧 → SfM → MVS | **未实现** | 先从视频抽取合适帧，再处理图像序列；视频文件本身不会自动产生可靠房间模型。 |
| 模板与尺寸录入 | 已有手动入口 | 不依赖 AR 跟踪，用户继续录入房间、门窗、家具与目标；不是照片重建的替身证据。 |

COLMAP 的官方教程要求重叠视点、清楚纹理、合适光照并避免模糊，建议对象至少在三张图像中出现；视频可降低抽帧频率，继续作为照片序列输入。相机在不同位置移动才有助于几何恢复，不能只拿大量相近模糊画面保证成功。[COLMAP 采集与 SfM/MVS 教程](https://colmap.github.io/tutorial.html)

下列是依据这套路线的工程推论与后续设计事项，**不是当前功能或验收结果**：

- 房间几何和对应特征应保持稳定；移动人物、反光、纯白墙、遮挡与重复纹理会使可靠对应和结构恢复变难。采集需要质量反馈与失败回退。
- 稀疏点云或密集网格要另经平面/墙角识别、二维投影、拓扑和门窗确认，才能转换为本产品可编辑的 Room。
- 米制尺寸需要额外尺度/参考约束设计，不能凭重建点云就宣称真实尺寸。官方地理配准通过至少三张已注册图像的相机中心三维对应来求相似变换，并设置 RANSAC 阈值；它说明真实坐标对齐需要外部参考，并不证明当前 APP 已有尺度恢复。[COLMAP 地理配准](https://colmap.github.io/faq.html#geo-registration)
- 当前没有 COLMAP/SfM/MVS 集成或手机端性能结论。本轮只记录技术区别；后续路线由独立 Issue 确定。
